# RabbitMQ

# 概念

RabbitMQ 是一个由 Erlang 语言开发的 AMQP 的开源实现

## AMQP 

Advanced Message Queue，高级消息队列协议。它是应用层协议的一个开放标准，为 面向消息的中间件设计，基于此协议的客户端与消息中间件可传递消息，并不受产品、开发语言 等条件的限制。RabbitMQ 中的交换器、交换器类型、队列、绑定、路由键等都是遵循的 AMQP 协议中相 应的概念。目前 RabbitMQ 最新版本默认支持的是 AMQP 0-9-1。

**AMQP 协议的三层**：

* **Module Layer**:协议最高层，主要定义了一些客户端调用的命令，客户端可以用这些命令实现自己的业务逻辑。
* **Session Layer**:中间层，主要负责客户端命令发送给服务器，再将服务端应答返回客户端，提供可靠性同步机制和错误处理。
* **Transport Layer**:最底层，主要传输二进制数据流，提供帧的处理、信道复用、错误检测和数据表示等。

**AMQP 模型的三大组件**：

* **交换器 (Exchange)**：消息代理服务器中用于把消息路由到队列的组件。
* **队列 (Queue)**：用来存储消息的数据结构，位于硬盘或内存中。
* **绑定 (Binding)**：一套规则，告知交换器消息应该将消息投递给哪个队列。

# MQ作用和应用场景

消息队列（MQ）是种应用程序间的通信方法，它允许系统组件以异步的方式进行交互,在不同的应用场景下可以展现不同的作用：

1. 异步处理: 将耗时的操作异步化，主流程无需等待这些操作完成即可返回结果，极大地减少响应时间，提升用户体验和系统吞吐量。
    * 同步时，系统：校验信息 -> 写入数据库（用户核心数据）-> 等待、调用短信服务发送验证码(欢迎短信，不是登陆验证的验证码) -> 等待、调用邮件服务发送欢迎邮件 -> 等待、为新用户初始化积分账户 -> 等待、任何一个下游服务抖动（比如发邮件慢），都会导致用户注册接口超时、失败，体验极差。
    * 使用消息队列进行异步解耦后，当用户注册请求到来时，系统首先将用户信息存储到数据库，然后将发送短信或邮件的任务封装成消息发送到消息队列中，接着立即返回注册成功的结果给用户。之后，会有专门的消费者从消息队列中取出消息，并执行发送短信或邮件的操作。这样，发送短信或邮件的操作就与用户注册的主流程解耦开来，实现了异步处理。
2. 流量削峰: 在访问量剧增的情况下,应用仍然需要继续发挥作用,但是这样突发的流量并不常见,如果因为这些特殊情况增加太多的机器,会造成巨大的浪费.于是我们可以使用MQ这种组件,支撑突发的访问压力,不会让我们的数据库因为突发流量而崩溃.
    * 比如双十一等活动的特价秒杀,就可以使用MQ来控制流量,让请求在队列中排好队,系统根据自己的处理能力逐步处理这些请求.
3. 应用解耦：作为生产者与消费者之间的中间层，使系统间不直接依赖对方的接口和IP，而是统一依赖MQ，任一系统的重启、扩容、升级、甚至暂时不可用，都不会影响其他系统。
    * 紧耦合的噩梦​：用户下单 -> 订单系统通过 RPC/HTTP 直接调用 库存系统的扣减库存接口。
    * 如果库存系统正在发布新版本，重启了10分钟，那么这10分钟内所有下单请求都会失败，导致用户无法购买，​直接损失交易额。
    * 引入MQ后的松耦合​：用户下单 -> 订单系统：
      1. 生成订单记录（状态为“待扣库存”）。
      1. 向消息队列发送一条消息（Topic: `order-created`, Content: `{orderId: 10001, itemId: 888, skuId: 999, count: 1}`）。
      1. 返回用户“下单成功，正在处理中”。
      1. 库存系统订阅 `order-created`Topic，收到消息后执行扣减库存逻辑，成功后通过另一个消息通知订单系统更新订单状态为“已扣库存”。
      1. 带来的好处​：库存系统可以随时发布、扩容、甚至短暂宕机。期间所有下单请求都会转换成消息持久化在MQ中，等库存系统恢复后，会继续消费这些消息完成库存扣减，​业务0中断。订单系统和库存系统之间只剩下“订单消息”这个契约，没有直接的网络依赖。
4. 消息分发: 当多个系统需要对同一数据做出响应时,可以使用MQ进行消息分发
    * 比如支付成功后,支付系统可以向MQ发送信息,其他系统订阅该信息,无需轮询数据库.还可以起到一个类似广播的效果,通知所有订阅MQ的程序.
5. 延迟通知: 在需要在特定的时间后发送通知的场景中,可以使用MQ的延迟信息功能.
    * 比如在电子商务平台中，如果用户下单后定时间内未支付，可以使用延迟队列在超时后自动取消订单

# 常用MQ区别

1. Kafka：日志采集、用户行为追踪、流式计算、监控数据聚合
    1. 核心优势
        1. 吞吐量巨大​：设计目标就是处理海量数据，像一条双向八车道的高速公路，​每秒百万级消息 轻松应对，非常适合日志、监控数据采集这类场景。
        2. 数据堆积能力强​：消息直接持久化到磁盘，能承受长时间、海量的消息堆积​（保存几天甚至几周），并支持随时回溯重新处理，容错性好。
        3. 流处理生态成熟​：是大数据领域的标配，与 Flink、Spark Streaming 等流计算框架无缝集成，生态体系非常完善。
    2. 缺点
        1. 功能相对单一​：主要基于发布-订阅模式，消息路由策略不够灵活，不适合需要复杂路由规则的业务场景。
        2. 运维复杂度高​：需要关注副本同步、分区平衡等问题，​对运维团队的技术能力要求较高。
        3. 延迟相对较高​：采用批量处理机制，消息延迟通常在毫秒级别​，不适合对实时性要求极致的场景。
2. RabbitMQ

典型场景：微服务解耦、异步任务处理、需要灵活路由的业务系统

采用Erlang语言开发,MQ功能比较完善,且几乎支持所有主流语言,开源提供的界面也非常友好,性能较好,吞吐量达到万级,社区活跃度高,文档更新频繁.比较适合数据量没那么大,并发量没那么高的场景.

1. 核心优势
    1. 协议支持丰富​：原生支持 AMQP、MQTT、STOMP 等多种协议，跨语言、跨平台兼容性好，适合异构系统集成。
    2. 消息路由灵活​：通过 Exchange、Binding Key 机制支持直连、广播、主题、头部等多种路由模式，能应对复杂的消息分发需求。
    3. 运维管理便捷​：提供功能完善的 Web 管理界面​，可以直观查看队列状态、消息堆积情况，降低运维门槛。
1. 需要注意的点
    1. 吞吐量有瓶颈​：单机性能有限，吞吐量通常在万级/秒​，虽然可以通过集群扩展，但性能提升有上限。
    2. 大量堆积时性能下降​：设计侧重实时消费，当消息大量堆积时容易引起性能衰减。因为它主要是为实时处理而设计的，不是为海量持久化而设计的。
    3. 事务性能较差​：虽然支持事务，但开启后性能损耗明显，生产环境中不建议使用。
1. RocketMQ

典型场景：电商交易、金融业务、对吞吐量和事务一致性都有要求的核心系统

采用Java语言开发,在可用性,可靠性以及稳定性等方面都非常出色,吞吐量能达到十万级,在Alibaba集团内部广泛使用,但支持的客户端语言不多,产品较新文档较少, 且社区活跃度般.适合于大规模分布式系统,可靠性要求高,且并发量大的场景,比如互联网金融.

1. 核心优势：
    1. 事务消息支持完善​：​经过阿里双十一验证的金融级事务消息方案​，为电商、金融等对一致性要求高的场景提供可靠保障。
    2. 性能与可靠性兼得​：在高吞吐（十万级/秒）​、低延迟和高可用性之间取得了很好的平衡，支持同步/异步刷盘等多种可靠性策略。
    3. 对Java技术栈友好​：基于Java开发，方便国内Java技术团队进行深度定制和问题排查。
1. 缺点：
    1. 流处理生态待加强​：虽然具备基础流处理能力，但与Kafka相比，与主流流处理框架的集成深度和成熟度还有差距。
    2. 国际化程度有待提升​：作为Apache顶级项目，其主要应用和社区活动仍以国内为主。

# 核心概念和工作流程

## 组件/概念

![](/assets/VeoTbfRLyo2rP5xfj1qcW0p6npb.png)

* Server/Broker：
  * 接收客户端的连接，实现`AMQP`实体服务。
  * 表示消息队列服务器实体。一般情况下一个Broker可以看做一个RabbitMQ服务器。一个Broker包含多个vhost
* Connection：连接，应用程序与Server的网络连接，TCP连接。
* Channel：信道，多路复用连接中的一条独立的双向数据流通道。信道是建立在真实的 TCP 连接内地虚拟连接，AMQP 命令都是通过信道发出去的，不管是发布消息、订阅队列还是接收消息，这些动作都是通过信道完成。因为对于操作系统来说建立和销毁 TCP 都是非常昂贵的开销，所以引入了信道的概念，以复用一条 TCP 连接。信道（Channel）是生产者、消费者与 RabbitMQ 通信的渠道，且每条 TCP 链接上的信道数量没有限制。就是说 RabbitMQ 在一条 TCP 链接上建立成百上千个信道来达到多个线程处理，这个 TCP 被多个线程共享，每个信道在 RabbitMQ 都有唯一的 ID，保证了信道私有性，每个信道。
  >  Kafka 的 Producer/Consumer 直接使用 TCP 连接与 Broker 交互；RocketMQ 也类似，没有 Channel 的概念。这是 RabbitMQ 实现多路复用的关键。

* Message：消息，应用程序和服务器之间传送的数据，消息可以非常简单，也可以很复杂。由Properties和Body组成。Properties为外包装，可以对消息进行修饰，比如消息的优先级、延迟等高级特性。消息头则由一系列的可选属性组成，这些属性包括 routing-key（路由键）、priority（相对于其他消息的优先权）、delivery-mode（指出该消息可能需要持久性存储）等。；Body就是消息体内容。
* Virtual Host：虚拟主机，用于逻辑隔离，表示一批独立的交换器、消息队列和相关对象。一个虚拟主机里面可以有若干个Exchange和Queue，同一个虚拟主机里面不能有相同名称的Exchange或Queue。
  > RabbitMQ 独有的概念。 Kafka 通过 Topic 来实现逻辑隔离，没有虚拟主机的概念。 RocketMQ 类似。

* Exchange：交换器，接收消息，按照路由规则将消息路由到一个或者多个队列。如果路由不到，或者返回给生产者，或者直接丢弃。`RabbitMQ`常用的交换器常用类型有direct、topic、fanout、headers四种，后面详细介绍。
  > Kafka 中没有 Exchange，生产者直接指定 Topic 发送消息。 RocketMQ 中也没有。

* Binding：绑定，交换器和消息队列之间的虚拟连接，一个绑定就是基于路由键将交换器和消息队列连接起来的路由规则，绑定中可以包含一个或者多个`RoutingKey`，Binding 信息被保存到 exchange 中的查询表中，用于 message 的分发依据。
  > 在 Kafka 中，Topic 的每个 Partition 直接对应磁盘文件，概念上更简单。

* RoutingKey：路由键，生产者将消息发送给交换器的时候，会发送一个`RoutingKey`，用来指定路由规则，这样交换器就知道把消息发送到哪个队列。路由键通常为一个“.”分割的字符串，例如`“com.rabbitmq”`。
* Queue：消息队列，用来保存消息，供消费者消费。它是消息的容器，也是消息的终点。一个消息 可投入一个或多个队列。消息一直在队列里面，等待消费者连接到这个队列将其取走。
  > 在 Kafka 中叫 Topic（逻辑概念），每个 Topic 由多个 Partition（分区）组成，这才是真正的存储单元。


## 工作流程

1. 生产者连接到 Server，建立一个连接，开启一个信道。
2. 生产者声明交换器和队列，设置相关属性，并通过路由键将交换器和队列进行绑定。
3. 消费者也需要进行建立连接，开启信道等操作，便于接收消息。
4. 生产者发送消息，发送到服务端中的虚拟主机。
5. 虚拟主机中的交换器根据路由键选择路由规则，发送到不同的消息队列中。
6. 订阅了消息队列的消费者就可以获取到消息，进行消费。

## 基本步骤(简单模式)

1. 创建连接工厂


```Java
ConnectionFactory factory = new ConnectionFactory();
```

1. 设置参数


```Java
factory.setHost("192.168.83.129");
factory.setPort(15672);
factory.setVirtualHost("/idetest");
factory.setUsername("guest");
factory.setPassword("guest");
```

1. 获取连接


```Java
Connection connection = factory.newConnection();
```

1. 创建信道


```Java
Channel channel = connection.createChannel();
```

1. 创建队列


```Java
channel.queueDeclare(String queue, boolean durable, boolean exclusive, boolean autoDelete, Map<String, Object> arguments)
        queue       队列名
        durable     是否持久化
        exclusive   是否独占(只能有一个消费者监听此队列)，Connection关闭后是否删除此队列
        autoDelete  没有Consumer时是否自动删除
        arguments   参数信息
```

1. 生产者发送消息


```Java
channel.basicPublish(String exchange, String routingKey, BasicProperties props, byte[] body)
        exchange    交换机名称，简单模式为""
        routingKey  路由键，简单模式与队列名相同
        props       配置信息
        body        消息数据(字节数组)
```

1. 消费者接收消息


```
com.rabbitmq.client.Consumer consumer = new DefaultConsumer(channel)
{   
    @Override
    public void handleDelivery(String consumerTag, Envelope envelope, AMQP.BasicProperties properties, byte[] body) throws IOException
    {
        super.handleDelivery(consumerTag(消息标识), envelope(获取交换机、路由等信息), properties(配置), body(接收到的数据));
    }
};

channel.basicConsume(String queue, boolean autoAck, Consumer callback)
    queue       队列名称
    autoAck     是否自动确认
    callback    回调对象,收到消息后自动执行handleDelivery方法。
```

1. 生产者关闭资源


```
    (生产者)释放资源
    channel.close();
    connection.close();   
```

## 交换机(Exchange)类型 

Exchange 分发消息时根据类型的不同分发策略有区别，目前共四种类型：direct、fanout、topic、headers 。

* headers 匹配 AMQP 消息的 header 而不是路由键，此外 headers 交换器和  direct 交换器完全一致，但性能差很多，目前几乎用不到了，所以直接看另外三种类型
* Direct：消息中的路由键（routing key）如果和 Binding 中的 binding key 一致，  交换器就将消息发到对应的队列中。它是完全匹配、单播的模式。
* Fanout：每个发到 fanout 类型交换器的消息都会分到所有绑定的队列上去。很像子网广播，每台子网内的主机都获得了一份复制的消息。fanout 类型转发消息是最快的。
* topic 交换器：topic 交换器通过模式匹配分配消息的路由键属性，将路由键和某个模式进行匹配，此时队列需要绑定到一个模式上。它将路由键和绑定键的字符串切分成单词，这些单词之间用点隔开。它同样也会识别两个通配符：符号“#”和符号 “.”。#匹配0个或多个单词，.匹配不多不少一个单词。+

## Work Queues(工作队列)

与入门程序的简单模式相比，多了一个或一些消费端，多个消费端共同消费同一个队列中的消息，依旧使用默认交换机。一个队列中如果有多个消费者，那么消费者之间对同一个消息的关系是竞争关系。

(隐患：高并发情况下,默认会产生某一个消息被多个消费者共同使用,可以设置一个开关(syncronize) 保证一条消息只能被一个消费者使用)。

重复消费原因：消费者没有发送 `basicAck`确认消息处理完成，或者basicAck发送失败了，queue认为消息没有被正确消费，又重新发了一遍。

![](/assets/KHvwbXbicoUaNexQVXOcXZMgnfd.png)

**channel.basicConsume("work_queues",false,consumer);**

## Routing路由模式

1. 队列与交换机绑定，不是任意的绑定了，而是指定一个RoutingKey（路由key）
2. 消息的发送方向在Exchange 发送消息时，也必须指定消息的的RoutingKey

4. 此模式声明的交换机类型为Direct
5. 可以绑定多次，指定不同的RoutingKey

# 消息顺序性

**“同一个业务 Key 下的消息有序”**，而不是 **“所有消息全局有序”**

![](/assets/R7uabWLDfokSGPxvEbPchwstnwf.png)

## 错乱场景

1. 一个queue，有多个consumer去消费，这样就会造成顺序的错误，consumer从MQ里面读取数据是有序的，但是每个consumer的执行时间是不固定的，无法保证先读到消息的consumer一定先完成操作，这样就会出现消息并没有按照顺序执行，造成数据顺序错误。

![](/assets/Fy5XbnkGioIgeWxZHj4cjQymnUh.png)

1. 一个queue对应一个consumer，但是consumer里面进行了多线程消费，这样也会造成消息消费顺序错误。

![](/assets/SQHwbkKKfoy1BqxnOHncGih8nVc.png)

## 顺序方案

消息顺序性保障分为:局部顺序性保证和全局顺序性保证. 

* 局部顺序性通常指的是在单个队列内部保证消息的顺序.
  * 常用方案：队列分区+单独消费者-相对而言, 局部顺序性更常见,也更容易实现.单个消费者的吞吐太低了,当需要多个消费者以提高处理速度时,可以使用分区消费.把个队列分割成 多个分区,每个分区由一个消费者处理,以此来保持每个分区内消息的顺序性.(分区消费)。根据业务字段（如订单ID哈希）将消息路由到不同队列，每个队列由独立消费者处理，保证分区内顺序。
    同一分区内，消息的key是一样的，但是处理类型不同。不同分区的处理流程都是一样的。
  ![](/assets/ZbOXbKPYEotQezxeaGtc40Rlnke.png)

  ![](/assets/TPu6b5QVBohg31xdnYqcvqn9nmh.png)

  * 容错/兜底：即使保证了顺序，也可能因为网络抖动、消费者宕机、重复投递导致乱序或重复。
    还可以考虑采用消息确认机制,在消息体中包含序列号，消费者端根据序列号判断消息顺序并处理。消费者在处理完条消息后,显式地发送确认,这样RabbitMQ才会移除并继续发送下一条消息。死信队列的声明和普通队列差不多。
    顺序消费一旦遇到异常（消息丢失/乱序/延迟），需要兜底：
    * **定时任务对账**：比如订单表和消息表对比，发现状态缺失则补发。
    * **幂等接口补偿**：消费失败的消息补偿时，不会破坏顺序（只更新更大的版本号）。
  ![](/assets/GJYzbChy5okzBwxpHrpcvyMxn3g.png)

  * 集群下的路由：
    工程实践：
    * 用 **一致性 Hash 交换机插件（Consistent Hash Exchange）**，根据 Key 进行路由；
    * 确保相同 Key 的消息落在同一个队列 → 同一个节点；
    * 避免不同节点的乱序问题。
* 全局顺序性是指在多个队列或多个消费者之间保证消息的顺序.
  * 消费者端重排序：在实际应用中,全局顺序性很难实现,可以考虑使用业务逻辑来保证顺序性,比如在消息中嵌入全局唯一序列号, 并在消费端进行排序处理.比如在购买商品的时候商品有唯一的可以排序订单号,我们可以通过查看该订单号的前一条和后一条是否已经被消费,再考虑是否消费该信息.(业务逻辑控制)
  
```Java
@Component
public class OrderReorderingConsumer {

    // 使用一个有序映射来缓存消息，键为序列号，值为消息内容和通道信息
    private final ConcurrentSkipListMap<Long, PendingMessage> pendingMessages = new ConcurrentSkipListMap<>();
    private long expectedSequenceNumber = 1L; // 期望的下一个序列号

    @RabbitListener(queues = "order_queue")
    public void handleMessage(Message message, Channel channel) throws IOException {
        // 假设消息头中包含序列号
        Long receivedSequenceNumber = (Long) message.getMessageProperties().getHeaders().get("sequence_id");
        String msgBody = new String(message.getBody());

        // 将消息放入缓存池
        pendingMessages.put(receivedSequenceNumber, new PendingMessage(msgBody, channel, message.getMessageProperties().getDeliveryTag()));

        // 尝试按顺序处理缓存池中的消息
        processInOrder();
    }

    private void processInOrder() {
        // 从缓存池中按序检查
        while (!pendingMessages.isEmpty()) {
            Map.Entry<Long, PendingMessage> firstEntry = pendingMessages.firstEntry();
            Long sequenceNumber = firstEntry.getKey();
            PendingMessage pendingMessage = firstEntry.getValue();

            if (sequenceNumber == expectedSequenceNumber) {
                // 是期望的消息，立即处理
                try {
                    System.out.println(" [按序处理] 序列号(" + sequenceNumber + "): " + pendingMessage.content);
                    // ... 处理业务逻辑 ...
                    // 确认消息
                    pendingMessage.channel.basicAck(pendingMessage.deliveryTag, false);
                    // 从缓存中移除已处理的消息
                    pendingMessages.remove(sequenceNumber);
                    // 期望的序列号加一
                    expectedSequenceNumber++;
                } catch (Exception e) {
                    System.err.println("按序处理消息失败: " + e.getMessage());
                    break; // 跳出循环，等待下次触发
                }
            } else {
                // 不是期望的消息，先跳出循环，等待前面的消息
                break;
            }
        }
    }

    // 内部类，用于保存 pending 消息的信息
    private static class PendingMessage {
        final String content;
        final Channel channel;
        final long deliveryTag;

        PendingMessage(String content, Channel channel, long deliveryTag) {
            this.content = content;
            this.channel = channel;
            this.deliveryTag = deliveryTag;
        }
    }
}
```

# 可靠性保证

https://www.cnblogs.com/RealBeBetter/p/17322762.html

## 消息丢失的情况

1. **生产者问题，消息到 MQ 的过程中搞丢：**因为应用程序故障,网络抖动等各种原因,生产者没有成功向broker发送消息.
2. **消息中间件自身问题，MQ 自己搞丢：**生产者成功发送给了Broker,但是Broker没有把消息保存好(如重启且没有持久化),导致消息丢失.
3. **消费者问题，MQ 到消费过程中搞丢**.Broker发送消息到消费者,消费者在消费消息时,因为没有处理好(宕机或程序故障),导致broker将消费 失败的消息从队列中删除了.

## 生产者->Server消息丢失解决方案(情况1)

> **必须项**：业务写 + Outbox 同事务；Dispatcher + Publisher Confirms；消费端必做幂等。
> **Broker 配置**：队列 durable、使用 QuorumQueue（关键业务）。
> **退化路径**：若 DB 可用但 MQ 不可用 -> 写入 outbox 并返回成功（最终一致性）；若 DB 不可用 -> 写入本地磁盘队列或拒绝请求并告警（取决于业务 SLA）


### 网络抖动/RabbitMQ 节点宕机/Channel或Connection 异常关闭导致的丢失/topic失败

#### 同步发送 + 重试（较弱保障）

**适用**：对延迟敏感但容忍少量复杂性的场景（非资金）。
**策略**：

* 在发送时做同步重试（短次数、指数回退），并开启客户端自动重连与心跳；若重试后仍失败则写入 outbox 或本地持久化队列。
* **风险**：如果消息在“发送后等待 ack”阶段网络断导致不确定性，仅靠同步重试会导致重复或丢失（需结合幂等）。

#### **事务性本地消息表（Outbox）**

把“业务写入 + 待发消息写入”放在同一 DB 事务中（核心保障）。

**适用**：关键业务（订单、支付、资金、库存），需要强可靠性。
**原理**：业务写入与写“待发消息”到 outbox 在同一个 DB 事务中完成（双写但在同事务），确保业务数据与消息状态一致；异步 Dispatcher 扫描 outbox 并把消息发送到 RabbitMQ。

事务内同时写业务表 + outbox 表；若业务 DB 与 outbox 不在同一 DB，需要两段提交问题（复杂），优先把 outbox 放在业务 DB 内。

**优点**：避免因 Producer 崩溃/网络导致的消息丢失；可重试；可审计。

**缺点**：复杂度与延迟（取决于 Dispatcher 扫描策略）；需要清理历史记录。

**流程**：

1. Outbox 表（示例 schema）


```SQL
CREATE TABLE outbox (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  msg_id VARCHAR(64) NOT NULL UNIQUE,   -- 全局唯一
  biz_key VARCHAR(128),                  -- 业务分片 key（用于顺序）
  exchange VARCHAR(128),
  routing_key VARCHAR(128),
  payload TEXT,                          -- 或存 pointer 指向对象存储
  status VARCHAR(16) DEFAULT 'PENDING',  -- PENDING, SENDING, SENT, FAILED
  attempts INT DEFAULT 0,
  next_retry_at DATETIME,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  sent_at DATETIME,
  last_error TEXT,
  lock_owner VARCHAR(64),
  lock_expire DATETIME,
  INDEX(status, next_retry_at),
  INDEX(biz_key)
);
```

1. 写入(事务内)：在同一个 DB 事务内：写业务表（比如 orders），同时插入 outbox 记录（status=PENDING）。提交 -> 业务与 outbox 保证一致。
2. Dispatcher（投递）要点：
    * 扫描 `status='PENDING' AND next_retry_at <= now()`，按 `created_at` 或 `biz_key` 排序发送，使用批量/并发分片（按 biz_key hash 分片，保证同 key 顺序）。
    * 发送时将状态置为 `SENDING` 并记录 `lock_owner` 与 `lock_expire`（lease pattern），避免多个 dispatcher 重发。
    * 采用 Publisher Confirm（或等待确认的回调）成功后更新 `status='SENT'` 并记录 `sent_at`。失败则更新 `attempts` 并计算 `next_retry_at`（指数回退）。
      * 如果没有确认丢失：Dispatcher 发送后没有收到 Confirm（网络中断），但 Broker 实际可能已写入。
        * Dispatcher 不把记录标为 `SENT` 直到 ConfirmCallback 明确 ACK；如果超时未收到 ACK，把 `status` 留为 `PENDING`/`SENDING` 并设置重试策略（消费端幂等）。
        * 设定较长的重试等待与合理 attempts 限制。
        * 在回滚/重试逻辑中始终携带 `msg_id`，保证消费端去重。
    * 对于长时间 `SENDING` 且超过 `lock_expire` 的记录，允许其他 dispatcher 抢占并重试。
      * 并发dispatcher/抢占实现：使用原子 UPDATE+WHERE 获得领取权
        
```SQL
UPDATE outbox
SET status='SENDING', lock_owner='dispatcher-1', lock_expire=DATE_ADD(NOW(), INTERVAL 1 MINUTE)
WHERE id IN (
  SELECT id FROM (
    SELECT id FROM outbox
    WHERE status='PENDING' AND next_retry_at <= NOW()
    ORDER BY created_at
    LIMIT 100
  ) tmp
);

```


**边界：**

1. **DB 与 MQ 同时不可用**：
    * 优先保证业务数据一致性：业务写失败需拒绝请求或降级（例如返回 503 给客户端），或写入本地磁盘临时队列并异步重试（但需人工恢复流程）。
2. **Outbox 表无限膨胀**：
    * 定期清理 `SENT` / `FAILED`（归档到冷表），设置 TTL。
    * 对长期 `FAILED` 的记录创建工单并人工干预。
3. **Dispatcher 崩溃导致 SENDING 永远卡住**：
    * 使用 `lock_expire` 和异步回收逻辑：若 `SENDING` 超过 lease，则允许其他 dispatcher 回收并重试。
4. **消息可能重复（ACK 未确定）**：
    * 强制消费端幂等；把 msg_id 作为持久化唯一索引；必要时在 outbox 中记录 brokerDeliveryTag 等（有助于排查）。

#### 本地持久化队列 / 文件系统 + 后台重放

**适用**：当 DB 不可用或不想耦合业务 DB（极端可用场景）。
**实现**：使用轻量的磁盘队列（Chronicle Queue、embedded RocksDB、leveldb、local append-only file），写文件作为持久化后由 dispatcher 发送。
**优点**：不依赖中心 DB；写入速度快；恢复后能重放。
**缺点**：需要实现索引、排重、备份、清理，运维复杂；跨进程一致性需要额外工作。

#### 借助 CDC（Change Data Capture）方案

**适用**：已有 DB 且想避免业务层显式 outbox 写入或降低改造。
**实现**：业务仅写业务表，CDC（Debezium）捕获业务表变更并流式写入 Kafka/RabbitMQ，或写入中间 Kafka 再同步到 RabbitMQ。
**优点**：解耦业务与消息投递，可靠性靠 CDC 平台保证。
**缺点**：引入 Kafka/Debezium 等复杂组件；延迟与运维成本。

* true:交换机无法将消息进行路由时，会将该消息返回给生产者
* false：如果发现消息无法进行路由，则直接丢弃

有了 mandatory 参数和回退消息，我们获得了对无法投递消息的感知能力，有机会在生产者的消息无法被投递时发现并处理。但有时候，我们并不知道该如何处理这些无法路由的消息，最多打个日志，然后触发报警，再来手动处理。而通过日志来处理这些无法路由的消息是很不优雅的做法，特别是当生产者所在的服务有多台机器的时候，手动复制日志会更加麻烦而且容易出错。

这时需要采用备份交换机了

备份交换机可以理解为 RabbitMQ 中交换机的“备胎”，当我们为某一个交换机声明一个对应的备份交换机时，

> 就是为它创建一个备胎，当交换机接收到一条不可路由消息时，将会把这条消息转发到备份交换机中，由备份交换机来进行转发和处理，通常备份交换机的类型为 Fanout ，这样就能把所有消息都投递到与其绑定的队列中，然后我们在备份交换机下绑定一个队列，这样所有那些原交换机无法被路由的消息，就会都进入这个队列了。当然，我们还可以建立一个报警队列，用独立的消费者来进行监测和报警。


#### 持久化

上面我们的角度是站在生产者的方向，但是如果服务器重启了，此时交换机和队列都不存在了，消息存在也发送不了，这时需要把交换机和队列都持久化。

然而，**即使队列和消息都是持久化的，也不能完全保证消息的 100% 不丢失**。例如：在消息尚未被刷写到磁盘时，RabbitMQ 服务器突然崩溃，这种情况下的消息仍然可能会丢失。此外，**RabbitMQ 不保证消息的立即持久化，而是尽可能快地将消息保存到磁盘**。因此，还需要做好生产者和消费者的 `消息确认机制` 以及通过 `集群` 的方式来实现 RabbitMQ 的高可用。

* 交换机持久化：
  * Spring中直接实例化对应的 `Exchange` 实现类即可，默认：**持久化的、非自动删除的**。
  ![](/assets/MpsmbMlPIogiHbx1oaScqMqjngf.png)

  * 在 RabbitMQ 的原生 API 中，例如：Java 客户端 API，声明持久化交换机时，需要将 `durable` 参数设置为 `true`：
  ![](/assets/B1sYbYmako0uuExqiALc7Qx6nBb.png)

  * 在 Spring AMQP 中，我们可以使用 `ExchangeBuilder` 来创建持久化的交换机

![](/assets/PhntbyyoWo9NQDxGeHDcOoK9nup.png)

* 队列持久化
  * 参见交换机持久化：new、channel.queueDeclare时设置参数、QueueBuilder
* 消息持久化
  如果队列是持久化的，发送到队列中的消息 **默认是持久化的**。我们也可以手动配置使消息持久化，需要在发送消息时设置消息属性为持久化：


* 死信机制+重试
  消息消费失败时：

  * 配合 **TTL + DLX** 实现延迟重试。
  避免消息因 Consumer 持续失败被无限循环投递。
  消息失败 → 重试 N 次（指数退避）。
  超过 N 次 → DLQ → 人工 / 异步补偿系统处理。
* 消息补偿机制保证消费端幂等性

# 消息积压

消息积压是指在消息队列(如RabbitMQ)中,待处理的消息数量超过了消费者处理能力,导致消息在队列中不断堆积的现象。消息生产太快，消费不过来，导致队列堆积很长，把服务器内存耗尽，这时RabbitMQ的处理能力很低下。

常见的消息积压原因：

1. 消息生产过快.在高流量或者高负载的情况下,生产者以极高的速率发送消息,超过了消费者的处理 能力.
2. 消费者能力不足.消费者处理处理消息的速度跟不上消息生产的速度,也会导致消息在队列中积压.比如消费端业务逻辑复杂,耗时长,消费端性能低,系统资源限制,异常处理不当等
3. 网络问题.出现网络延迟或者网络抖动,消费者无法及时或确认消息,最终导致消息积压.
4. RabbitMQ服务配置过低.

解决方案：

1. 提高消费者效率.
    1. 增加消费者实例数量,比如新增机器.
    2. 优化业务逻辑,比如使用多线程来处理业务/一批消息聚合处理/合理设置 prefetch
    3. 设置prefetchCount,当消费者阻塞时,消息转发到其他未阻塞的消费者.
        在 Work 模式中，默认情况下 RabbitMQ 采用轮询（round-robin）的方式将消息依次分发给各个消费者，即每个消费者会轮流接收到消息。但这种方式可能会导致性能不均衡，能力强的消费者可能会闲置，而能力弱的消费者可能会堆积大量任务。为了实现能者多劳，可以通过设置增大消费者的预取计数（prefetch count）来实现。
        创建QosListener类，实现ChannelAwareMessageListener接口
        在xml设置listener-container的prefetch="1"（每次只拉取1条消息，签收后才可以拉取下一条消息）
    4. 消息发生异常时,设置合适的重试策略,或者不要消费失败就重新放到队列里，而是转入到死信队列.
    5. **紧急上线专门用于记录消息的队列**，将消息先批量取出来，记录数据库，离线慢慢处理
2. 限制生产者速率:流量控制,限流算法.
    1. 流量控制:在消息生产者中实现流量控制逻辑,根据消费者处理能力动态调整发送速率.
    2. 限流:使用限流工具,为消息发送速率设置个上限.
    3. 设置过期时间.如果消息过期未消费,可以配置死信队列,以避免消息丢失,并减少对主队列的压力.
3. 资源与配置优化

升级RabbitMQ服务器硬件,调整配置参数等.

# 消息幂等性

在应用程序中,幂等性就是指对个系统进行重复调用(相同参数),不论请求多少次,这些请求对系统的**影响**都是相同的效果.

比如数据库的 select 操作.不同时间两次查询的结果可能不同,但是这个操作是符合幂等性的.幂等 性指的是对资源的影响,而不是返回结果.查询操作对数据资源本身不会产生影响,之所以结果不同,可 能是因为两次查询之间有其他操作对资源进行了修改.

对于MQ而言,幂等性是指同条消息,多次消费,对系统的影响是相同的.

不幂等的情况：

1. producer重试：Producer 端没收到 Broker 的 Confirm（其实 Broker 已写入），于是重发 → Broker 收到多条相同消息。
2. broker重发：消息已发送给 Consumer，但 Consumer crash 或 ACK 丢失 → Broker 认为未消费 → 重新投递。
3. consumer异常：消费逻辑报错，Nack/Requeue，消息被再次投递到之前的队列中。

## 投递语义和消费语义

一般消息中间件的消息传输保障分为三个层级.

1. At most once:最多1次.消息可能会丢失，但绝不会重复传输. 
    1. 场景：日志收集/监控指标/IoT硬件设备上报数据/推荐-广告曝光日志
    2. kafka-投递语义-消息最多投递一次：
        > <span style="color: #FBBFBC"><mark style="background-color: #F2F3F5">`Producer`</mark></span>不等待确认，只管发出即可；最可能丢失消息。如果丢了消息，就是投递0次。如果没丢，就是投递1次。

    3. kafka-消费语义-消息最多消费一次：
    ![](/assets/XE4SbSiwEo1gIfxy0l6c14zsnAb.png)

2. At least once:最少1次.消息绝不会丢失，但可能会重复传输.
    1. 适用场景：消息推送、生成报表等可容忍多执行一次的任务、db更新记录状态、
    2. kafka-投递语义-消息最少投递一次：
        > <span style="color: #FBBFBC"><mark style="background-color: #F2F3F5">`Producer`</mark></span>往<span style="color: #FBBFBC"><mark style="background-color: #F2F3F5">`kafka`</mark></span>的<span style="color: #FBBFBC"><mark style="background-color: #F2F3F5">`Leader（主）`</mark></span>节点发送消息后，会等<span style="color: #FBBFBC"><mark style="background-color: #F2F3F5">`follower(从)`</mark></span>节点同步完数据以后，再给<span style="color: #FBBFBC"><mark style="background-color: #F2F3F5">`Producer`</mark></span>返回ACK确认消息。

    3. kafka-消费语义-消息最少消费一次
    ![](/assets/J0dvblSZiotVtOxXvEbcb5iYn7g.png)

3. Exactly once:恰好1次.每条消息肯定会被传输1次且仅传输1次. RabbitMQ支持"最多一次"和"最少一次".
    1. 场景：
        1. 所有可幂等的场景，幂等表只能阻止“本地重复处理”，但资源已经被外部系统消耗了，就不可逆了。
        2. 一次性事件
            1. 合同只能一次签署，多次会出现多个合同，严重法律问题
            2. 彩票开奖，重复开奖会让不同用户拿到奖励
            3. 税务申报：重复提交到税务算违规
        3. 不可幂等调用的外部场景
            1. 调用外部不支持幂等号的支付接口，重复调用-重复支付
            2. 按条计费的服务商
    2. kafka-投递语义-消息恰好投递一次
        实现逻辑：
        * 每个生产者初始化时会获得一个唯一的 Producer ID（PID）（由 Kafka broker 分配，对用户透明）。
        * 生产者向每个分区发送消息时，会为消息分配一个递增的序列号（Sequence Number），每个分区独立计数（从 0 开始）。
        * Kafka broker 收到消息后，会记录每个 PID 对应分区的最新序列号：
          * 若新消息的序列号 = 上次记录 + 1，说明是新消息，正常存储并返回 ACK；
          * 若序列号 ≤ 上次记录，说明是重复消息（如生产者重试导致），直接丢弃并返回 ACK（避免重复存储）。
        局限：仅保证单个生产者会话内、单个分区的幂等性，无法跨分区或跨生产者会话（如生产者重启后 PID 可能变化）。
    3. kafka-消费语义-消息恰好消费一次
        满足幂等性即可
    4. rabbitmq实现恰好一次
    ![](/assets/GlqObWvploIoZlxrljucuZ5LnXf.png)


## 解决方案

1. 全局唯一ID
    1. 为每条消息分配个唯一标识符,比如UUID或者MQ消息中的唯一ID,但是定要保证唯一性.
    2. 消费者收到消息后,先用该id判断该消息是否已经消费过,如果已经消费过,则放弃处理.
    3. 如果未消费过,消费者开始消费消息,业务处理成功后,把唯一ID保存起来(数据库或Redis等)
2. 业务逻辑判断

在业务逻辑层面实现消息处理的幂等性. 例如:通过检查数据库中是否已存在相关数据记录,或者使用乐观锁机制来避免更新已被其他事务更改的数据,再或者在处理消息之前,先检查相关业务的状态,确保消息对应的操作尚未执行,然后才进行处理,具体根据业务场景来处理.

例子：队列Q1中可能会有多条一模一样的消息，当消费者的服务恢复正常之后，Q1队列中这些一样的消息都会被Q1读取并进行业务处理。此时如果消费者没有幂等性的保证的话，就会出现“多扣钱”的问题。

# 死信队列

死信队列是一个专门用于接收无法被消费者正确处理的消息的队列。当消息被投递到死信队列时，可以进行一些特殊的处理操作，比如记录日志、发送告警等。同时，死信队列也可以配置一些特定的参数，比如过期时间、最大长度等，用于控制消息的生命周期。

## TTL

消息到达存活时间后没有被消费，会被自动删除。有两种设置方法：

![](/assets/UpBsb2UWlopVPMxaMDEcPmYsnOc.png)

1. 队列统一过期

声明队列时设置队列10s后统一过期

1. 消息单独过期

发送消息时，通过MessagePostProcessor对象设置过期


```
rabbitTemplate.convertAndSend("test_exchange_ttl", "ttl.otto", "hello ttl!" + i, new MessagePostProcessor()

        }
    });
```

消息和队列同时设置过期时间时,以时间短的为准

出于性能考虑,只有消息处于队列顶端(被消费)时才会判断是否过期

## DLX

DLX:Dead Letter Exchange 死信交换机，当消息成为Dead message后,可以被重新发送到另一台交换机,这个交换机就是DLX。

1. 队列消息长度达到限制
2. 消费者拒收消息，basicNack/basicReject且requeue=false
3. 消息到达过期时间未被消费

# 消息补偿

我们通过之前的消息可靠性投递 , ACK 确认机制 , 以及死信队列 , 基本上已经能够保证消息投递成功了 !

为什么还要消息补偿机制呢？ 难道消息还会丢失，没错，系统是在一个复杂的环境，不要想的太简单了，虽然以上的三种方案，基本可以保证消息的高可用不丢失的问题，但是作为有追求的程序员来讲，要绝对保证我的系统的稳定性，有一种危机意识。仅依赖 RabbitMQ 自身的机制可能无法完全保证消息的可靠性，因此需要消息补偿机制来进一步确保消息的最终一致性。

比如：持久化的消息，保存到硬盘过程中，当前队列节点挂了，存储节点硬盘又坏了，消息丢了，怎么办？

产线网络环境太复杂，所以不知数太多，所以要做消息补偿机制 !

## 消费端幂等性保证

这是最基础、最重要的防线，是其他补偿机制能够安全运行的基石。兜底

* 机制： 保证无论同一条消息被消费多少次，最终的效果与只消费一次是相同的。
* 如何实现：
  * 唯一标识： 为每条消息分配一个全局唯一的ID（如业务主键、雪花算法ID等）。
  * 状态检查： 在执行业务逻辑前（如扣减库存、更新余额），先检查这个唯一ID是否已经被处理过。
  * 存储记录： 将已处理消息的ID持久化到数据库（如Redis Set/String， 数据库表），后续请求先查此记录。
* 场景： 应对任何可能的消息重复（网络重传、生产者重发、消费者重启等）。
* 关键点： 这是业务逻辑必须实现的，不是中间件功能。

## 本地事务表 + 消息队列

**Producer Outbox**

* 生产端用 Outbox 表（事务性本地消息表），定时扫描未投递成功的消息，补偿性投递 MQ。

**Consumer Outbox**

* 消费端先写本地消息表（标记消息处理状态），如失败可重试或人工补偿。

## 异步确认与重试 (Ack & Retry)

这是消息中间件本身提供的基础补偿能力。

* 机制：
  * 消费者ACK： 消费者成功处理消息后，向MQ发送一个确认（Ack），MQ才会删除该消息。
  * NACK/Reject： 如果处理失败，消费者可以告知MQ处理失败（Nack），MQ可以将消息重新放回队列或放入死信队列。
  * 自动重试： MQ在未收到Ack时，会按照一定策略（如间隔1s, 5s, 10s）重新投递消息。
* 场景： 处理消费者端的临时性故障，如网络抖动、依赖服务短暂不可用、数据库死锁等。
* 关键点： 必须与消费端幂等性配合使用，否则重试会导致消息重复。

## 死信队列 (Dead-Letter Queue, DLQ)

重试机制的补充，用于处理“无法被正常消费”的消息。

* 机制： 当消息达到最大重试次数后，MQ会自动将其转移到另一个特殊的队列，即死信队列。
* 如何实现：
  * 监控死信队列，会有报警通知开发人员。
  * 开发人员可以查看死信消息的内容、失败原因，进行人工干预或通过其他方式修复数据。
* 场景： 处理因消息格式错误、业务逻辑存在永久性BUG（如账户不存在）、下游服务长期不可用等导致的永远失败的消息。

## 对账与核对 (Reconciliation)

这是最终的大招，一种离线、周期性的强力补偿手段，不依赖业务本身的代码逻辑。

* 机制： 在事后（例如每天凌晨），通过跑批作业，比对上下游两个系统的数据是否一致，并对不一致的数据进行修补。
* 如何实现：
  * 全量对账： 比对两个系统在某个时间切面上的全部相关数据。
  * 增量对账： 只比对周期内产生的业务数据。
  * 修复： 发现不一致（如支付成功了但订单未完结），通过调用补偿接口（如补单）或人工方式修复数据。
* 场景： 用于弥补上述所有实时机制可能遗漏的极端情况，是保障财务、交易等核心数据最终一致性的最后一道防线。
* 关键点： 延迟高，但覆盖全面，非常可靠。

# 延迟队列

延迟队列(DelayedQueue)，即消息被发送以后,并不想让消费者立刻拿到消息,而是等待特定时间后, 消费者才能拿到这个消息进行消费.

1. 使用死信队列达到延迟队列的效果.
    **实现：**不给原队列（正常队列）设置消费者，当消息在原队列中达到 TTL 后，由于还未被消费，则会被转发到绑定的死信交换器，消费者从死信队列中消费消息，从而实现消息的延迟处理。
    2. 优点: 灵活不需要额外的插件支持.
    3. 缺点: 
        1. 存在消息顺序问题.
            因为队列的特点就是先进先出，如果发送的消息延迟的时间不同，例如第一个延迟 10s、第二个延迟 5s、第三个延迟 1s。
            那么后面的消息，需要等 10s 的消息消费完才能消费。当 10s 消息未被消费，则后续的消息都会被阻塞，即使消息设置了更短的延迟。
        2. 需要额外的逻辑来处理死信队列的消息,增加了系统的复杂性.
        3. **解决方案：拆分延迟队列**，按延迟时间分类，例如 5s、30s、5min、30min 多个队列
        ![](/assets/QWlDb3wh9ouxeWx6qtXc6Icpngg.png)

2. 使用RabbitMQ官方提供的延迟队列插件
    **实现：**延迟消息插件（rabbitmq-delayed-message-exchange）。在发送消息时，指定消息的延迟时间，RabbitMQ 会在消息达到延迟时间后将其转发到对应的队列进行消费。
    插件原理：
    *插件提供了一种新的交换器类型*<span style="color: #C0ECBC">`*x-delayed-message*`</span>*。这种交换器可以像普通的交换器一样，接收消息并根据路由键将消息路由到相应的队列。只不过*<span style="color: #C0ECBC">`*x-delayed-message*`</span>*类型的交换机接收消息投递后，不会直接路由到队列中，而是存储到 Mnesia(Mnesia 是*<span style="color: #C7D5F6">*Erlang*</span>*运行时中自带的一个*<span style="color: #C7D5F6">*[数据库管理](https://cloud.tencent.com/product/dmc?from_column=20065&from=20065)*</span>*系统)中。*
    *等到消息达到可投递时间，消息才会被投递到目标队列中。*
    5. 优点:  通过插件可以直接创建延迟队列,简化延迟消 息的实现.避免了DLX的时序问题.
    6. 缺点:  需要依赖特定的插件,有运维工作.只适特定版本.
    # 推拉模式

    RabbitMQ支持两种消息传递模式:推模式(push)和拉模式(pull).
    ## 推拉模式概念

    推模式：消息中间件主动将消息推送给消费者.实时性要求高的业务，如订单支付通知、推送消息、日志采集。
    拉模式：消费者主动从消息中间件拉取消息.
    推模式（push）
    1：推模式接收消息是最有效的一种消息处理方式。channel.basicConsume(queneName,consumer)方法将信道(channel)设置成投递模式，直到取消队列的订阅为止；在投递模式期间，当消息到达RabbitMQ时，RabbitMQ会自动地、不断地投递消息给匹配的消费者，而不需要消费端手动来拉取，当然投递消息的个数还是会受到channel.basicQos的限制。
    2：推模式将消息提前推送给消费者，消费者必须设置一个缓冲区缓存这些消息。优点是消费者总是有一堆在内存中待处理的消息，所以当真正去消费消息时效率很高。缺点就是缓冲区可能会溢出。
    3：由于推模式是信息到达RabbitMQ后，就会立即被投递给匹配的消费者，所以实时性非常好，消费者能及时得到最新的消息。
    拉模式（pull）大批量离线数据处理（日志清洗、报表生成）。消费端处理速度不稳定、需要批量处理的业务。
    1：如果只想从队列中获取单条消息而不是持续订阅，则可以使用channel.basicGet方法来进行消费消息。
    2：拉模式在消费者需要时才去消息中间件拉取消息，这段网络开销会明显增加消息延迟，降低系统吞吐量。 
    3：由于拉模式需要消费者手动去RabbitMQ中拉取消息，所以实时性较差；消费者难以获取实时消息，具体什么时候能拿到新消息完全取决于消费者什么时候去拉取消息。

## 消息追踪

在使用任何消息<span style="color: #C7D5F6">[中间件](https://cloud.tencent.com/product/message-queue-catalog?from_column=20065&from=20065)</span>的过程中，难免会出现某条消息异常丢失的情况。对于 RabbitMQ 而言，可能是因为生产者或消费者与RabbitMQ 断开了连接，而它们与 RabbitMQ 又采用了不同的确认机制；也有可能是因为交换器与队列之间不同的转发策略；甚至是交换器并没有与任何队列进行绑定，生产者又不感知或者没有采取相应的措施；另外 RabbitMQ 本身的集群策略也可能导致消息的丢失。这个时候就需要有一个较好的机制跟踪记录消息的投递过程，以此协助开发和<span style="color: #C7D5F6">[运维](https://cloud.tencent.com/solution/operation?from_column=20065&from=20065)</span>人员进行问题的定位。

在RabbitMQ中可以使用Firehose和rabbitmq_ tracing插件功能来实现消息追踪。

### Firehouse

使用rabbitmqctl trace_on/rabbitmqctl trace_off开启/关闭

* firehose的机制是将生产者投递给rabbitmq的消息，rabbitmq投递给消费者的消息按照指定的格式发送到默认的exchange上。
* 这个默认的exchange的名称为amg.abbitmq.trace,它是一个topic类型的exchange。
* 发送到这个exchange上的消息的routing key为publish.exchangename和deliver.queuename。
* 其中exchangename和queuename为实际exchange和queue的名称， 分别对应生产者投递到exchange的消息，和消费者从queue上获取的消息。
* 打开trace会影响消息写入功能，适当打开后请关闭。

### rabbitmq_ tracing

rabbitmq. tracing和Firehose在实现上如出一辙, 只不过rabbitmq _tracing的方式比Firehose多了一层GUI的包装，更容易使用和管理。

使用rabbitmq-plugins enable rabbitmq_tracing开启插件，可以使用图形化界面管理。

# 集群

## <span style="color: #E0E1E4">单机模式</span>

<span style="color: #E0E1E4">单机模式，即单机情况不做集群，就单独运行一个</span><span style="color: #FBBFBC">`rabbitmq`</span><span style="color: #E0E1E4">而已。就是 </span><span style="color: #FBBFBC">`Demo`</span><span style="color: #E0E1E4"> 级别的，一般就是你本地启动了玩的，没人生产用单机模式。</span>

## 普通集群模式

 在多台机器上启动多个 RabbitMQ 实例，而队列 queue 的消息只会存放在其中一个 RabbitMQ 实例上，但是每个实例都同步 queue 的元数据（元数据是 queue 的一些配置信息，通过元数据，可以找到 queue 所在实例）。

消费的时候，如果连接到了另外的实例，那么该实例就会从数据实际所在的实例上的queue拉取消息过来，就是说让集群中多个节点来服务某个 queue 的读写操作。

普通集群模式的缺点在于：无高可用性，主要是提高吞吐量，queue所在的节点宕机了，其他实例就无法从那个实例拉取数据；RabbitMQ 内部也会产生大量的数据传输。

![](/assets/CivSbqCptob9QWxhRgGc0oPznWe.png)

## 镜像集群模式

在镜像集群模式下，你创建的`queue`，无论元数据还是`queue`里的消息都会存在于多个实例上，就是说，每个 `RabbitMQ`节点都有这个`queue`的一个完整镜像，包含 `queue` 的全部数据的意思。然后每次你写消息到`queue`的时候，都会自动把消息同步到多个实例的`queue`上。

集群中一般会包含一个主节点master和若干个从节点slave，如果master由于某种原因失效，那么按照slave加入的时间排序，"资历最老"的slave会被提升为新的master。

所有的消息只会向master发送，再由master将命令的执行结果广播给slave，所以master与slave节点的状态是相同的。
